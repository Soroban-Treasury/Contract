## 1. Summary

**What holds up.** Every entry point that changes state calls `require_auth` for the owner it acts for, after checking that address is an owner; no entry point trusts a role passed by the caller. Spending is default-deny: an asset without a limit cannot be proposed or executed. The limit is checked when a proposal is made and again when it is executed, so lowering or removing a limit affects pending proposals. `execute` writes its state (proposal marked executed, period spend updated) before the token transfer, so a token that calls back finds the proposal already executed. Amount arithmetic is checked. Owner and policy counts are bounded, and each proposal is its own storage entry.

**What was fixed during this review.** F-01 (front-running of setup).

**What needs a decision.** F-02 to F-05 are design limits. They are acceptable for a first version, are documented for users, and are the places to look first in an external audit.

### F-01 (Medium, fixed): setup could be front-run

**Before.** Deploying and calling `initialize` were two transactions, and `initialize` had no authorization. Anyone watching the network could call it first with their own owners, after which the deployer's call failed with `AlreadyInitialized`. A deployer who funded the contract without reading its configuration back would have given the treasury to the attacker.

**Fix.** Setup moved to `__constructor`, which runs in the deployment transaction. There is no moment where the contract exists but is uninitialized. A constructor that fails aborts the deployment. The `initialize` function was removed; error code 1 is kept reserved. Tests: the `constructor_*` tests. Confirmed on testnet.

### F-02 (Low, accepted): fixed-window limit

The limit is per period starting at the first spend after the previous period ended. Spending the full limit at the end of one period and the full limit again right after it rolls over moves up to twice the limit in a short time. This is how fixed windows work. A sliding window would remove it at the cost of more storage and more complex arithmetic. **Guidance:** size the limit so that twice its value is acceptable to lose. Documented in the mainnet checklist.

### F-03 (Low, accepted): no owner rotation or recovery

Owners and threshold are set at deployment and cannot change. If enough keys are lost that fewer than `threshold` remain, the funds are locked. A leaked owner key cannot be removed. **Guidance:** choose owners and threshold with this in mind (see the checklist); to change owners, deploy a new treasury and move the funds. A rotation flow by proposal is a candidate for a later version.

### F-04 (Low, accepted): no cancel or revoke

Once a proposal has `threshold` approvals, any owner can execute it until it expires, and an approver cannot withdraw their approval. If an owner approves by mistake, the remedy is that the other approvers do not execute, and that the proposal expires. **Guidance:** use short proposal lifetimes for large payments. A `cancel` by the proposer or by threshold approval is a candidate for a later version.

### F-05 (Low, accepted): proposal spam

An owner can create any number of proposals. Each is a persistent entry kept for up to about 60 days. The cost falls on the owner who sends them, and the UI shows the newest 50. Owners are trusted, so this is a nuisance, not a theft risk.

### F-06 (Info): reads extend TTL

The internal loaders extend TTL when an entry is read, so a read in a real transaction also writes. It keeps active treasuries alive. Read-only simulations are unaffected.

### F-07 (Info): token trust

Owners decide which token contract a limit applies to. A malicious token contract could misbehave inside `transfer`. State is updated before the call, and the treasury exposes nothing a token can use to move other assets, so the impact is limited to that token's own balance.

### F-08 (Info): limit changes need several owners in one call

`set_spend_limit` and `remove_spend_limit` need `threshold` distinct owners to authorize one call. That is hard to coordinate and the SDK does not yet collect other owners' signatures, so limits are set at deployment. See the SDK README.

## 3. Checked and found fine

- **Authorization:** `propose`, `approve`, `execute`: the acting owner authorizes and is checked against `Config`. Policy changes: `threshold` distinct owners, each authorizing, no duplicates.
- **Replay and double execution:** `executed` is set before the transfer; a second `execute` returns `AlreadyExecuted`. Approvals are unique per owner.
- **Expiry:** boundary is inclusive (`now > expires_at` is expired), matching the app.
- **Arithmetic:** `checked_add` on spend, expiry and proposal count; `i128` amounts must be greater than zero.
- **Denial of service:** owners, policies and approvals are bounded; no loop over unbounded data.
- **Constructor input:** empty, duplicate, too many owners; bad threshold; zero limits; duplicate assets; too many limits are all rejected.

## 4. What an external audit should look at

- The interaction with arbitrary token contracts during `execute`.
- TTL and archival behaviour for a treasury that sits idle.
- Whether F-02 to F-04 are acceptable for the amounts you intend to hold.
- Anything this review is too close to the code to see.

This report does not replace an independent audit.
